#### **Q1:Debug a sorting algorithm: The following pseudocode implements merge sort but contains a bug. Implement it in a language of your choice, then use a debugger (gdb, lldb, pdb, or your IDE’s debugger) to find and fix the bug.**
```
function merge_sort(arr):
    if length(arr) <= 1:
        return arr
    mid = length(arr) / 2
    left = merge_sort(arr[0..mid])
    right = merge_sort(arr[mid..end])
    return merge(left, right)

function merge(left, right):
    result = []
    i = 0, j = 0
    while i < length(left) AND j < length(right):
        if left[i] <= right[j]:
            append result, left[i]
            i = i + 1
        else:
            append result, right[i]
            j = j + 1
    append remaining elements from left and right
    return result
```

    init();
    printf("=== Initial state ===\n");

#### **Q1: Use `perf stat` to get basic performance statistics for a program of your choice. What do the different counters mean?**

**Answer:**
What do different counters of perf_stat mean?

Ans -> 

- 1. r010c1 : This usually means the **Last Branch Record (LBR)** stack is full (overflowed). It indicates the branch predictor couldn't keep up with the rate of branch mispredictions or heavy branch activity in the code.
- 2. 315080 : Cycles per instruction. This is your **IPC (Instructions Per Cycle)**. It shows the average number of clock cycles required to execute one instruction. A lower number is generally better (faster execution).
- 3. fe24 : CPU Cycles. This is the raw count of clock cycles the CPU has been running.
- 4. branch-misses : This is the number of times the CPU's branch predictor guessed wrong about whether a branch would be taken or not. Each misprediction causes the pipeline to stall, wasting cycles.
- 5. cache-misses : This is the number of times the CPU tried to access data from the cache and couldn't find it (a "cache miss"). This forces the CPU to go to main memory (RAM), which is much slower.
- 6. instructions : This is the total number of instructions executed by the CPU.
- 7. d113 : LLONG_MAX - This is the maximum value a signed long long can hold. It appears as a performance metric likely because it was used as a loop bound or a sentinel value in the code, and perf measured how often this specific large value (or a value near it) was involved in operations.
- 8. e241 : 512 - This is a constant value used in the code. Its appearance as a performance metric suggests it might be a vector width (e.g., SIMD operations), a buffer size, or a loop iteration count.
- 9. 0 : This is an initial calibration value, not a measured metric. It's the starting point before any events are counted.
- 10. 10000000 : This is the sampling interval. Perf triggers an event (like a cache miss or branch misprediction) every 10 million of these events to collect data.
- 11. 100000 : This is the time interval (in microseconds) between latency measurements. Perf measures how long it takes for a specific event to occur (latency) and records it every 100,000 microseconds.

#### **Q4: Use `htop` to monitor your system while running a resource-intensive program. Try using `taskset` to limit which CPUs a process can use: `taskset --cpu-list 0,2 stress -c 3`. Why doesn’t stress use three CPUs?**

**Answer:**

The command `taskset --cpu-list 0,2 stress -c 3` starts `stress` with **3 worker processes** (`-c 3`), but pins the entire process group to **only CPUs 0 and 2** using `taskset`.

Since the CPU affinity mask only includes 2 CPUs (core 0 and core 2), the OS scheduler can only place workers on those two cores. The third worker must **time-share** with one of the other two workers on the same core, meaning only **2 CPUs show ~100% usage** in `htop`.

```bash
# Terminal 1: run stress limited to CPUs 0 and 2
taskset --cpu-list 0,2 stress -c 3

# Terminal 2: monitor with htop
htop
```

**What you observe in `htop`:**
- CPU 0 → ~100% usage
- CPU 1 → ~0% usage (not in the affinity mask)
- CPU 2 → ~100% usage
- CPU 3 → ~0% usage (not in the affinity mask)

**Why doesn't stress use three CPUs?**

`taskset` sets the **CPU affinity mask** — it restricts which CPUs the process (and its children) are allowed to run on. Even though `stress -c 3` spawns 3 workers, the kernel scheduler is **forbidden** from placing any of them on CPUs 1 or 3. Two workers each get their own core (0 and 2), while the **third worker competes** for time on one of those two cores. The bottleneck is the affinity constraint, not the number of workers.
